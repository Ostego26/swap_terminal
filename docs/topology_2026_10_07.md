## THREE GRIDCOIN WALLETS, AND ONLY ONE OF THEM IS THE DESK'S

Written down because I collapsed two of them three separate times on 2026-10-07
and it cost a round each time. Operator: "you keep forgetting we have 3 different
grc wallets on here. 2 gui wallets. one mainnet and one testnet and then the cli
daemon the swap terminal uses."

    port    what it is                        network   the terminal
    ------  --------------------------------  --------  ---------------------------
    25779   gridcoinresearchd -datadir=       TESTNET   YES -- this is the hot
            $HOME/.GridcoinResearch-desk                wallet every GRC payout
            (pid 2586595, measured 2026-10-07)          is sent from
    25715   the GUI wallet                    TESTNET   no
            (pid 340262, measured 2026-10-07)
    15715   the GUI wallet                    MAINNET   no, and NEVER
            (config.py's mainnet default)               REAL MONEY

WHAT EACH ONE IS FOR, and the only one with a balance worth quoting here is the
first, because it is the only one the terminal spends:

    25779   11.00248643 tGRC, measured 2026-10-07 22:40 via getwalletinfo from
            inside the container. `stake` 0.0, so nothing is maturing.
    25715   a separate testnet pot, and its balance is NOT quoted here because
            the desk cannot read it. Measured 2026-10-07: the same credentials
            that work on 25779 get `401 Client Error: Authorization Required`
            from 25715. That is the custody separation enforced at the RPC layer
            and not only by datadir -- two daemons, two rpcpassword values, and
            the desk holding one of them. wallet_custody.py's header names
            GRC_OPERATOR_RPC_* as the designed place for the operator's own
            endpoint, read "through gridcoin_credentials.operator_endpoint() and
            from nowhere else -- never a .conf, never a .env".

            It is the only place more tGRC for the desk can come from without a
            faucet, and a transfer from it is the operator's to run: it needs
            credentials this process does not have, by design.
    15715   NOT MEASURED AND DELIBERATELY SO. It holds real GRC, the operator's
            standing instruction for this work is TESTNET ONLY, and CLAUDE.md's
            live-safety rules put the operator's own live wallets off limits.
            wallet_custody.py already refuses a mainnet or unrecognized port
            rather than reading it, which is the behavior to copy and not to
            work around.

THE THREE CANNOT FUND EACH OTHER ACROSS A NETWORK BOUNDARY. 15715 and the two
testnet daemons are different chains; no protocol moves value between a mainnet
and a testnet, and no amount of configuration makes one. So "refill the hot
wallet from mainnet" is not a permissions question or a safety question -- it is
not a thing that exists. 25715 -> 25779 is an ordinary tGRC transfer and is the
only route that refills the desk.

AND BTC CANNOT FUND ANY OF THEM. BTC_RPC_PORT=18443 is a private REGTEST node
whose coins come from `generatetoaddress`. There is no market between regtest BTC
and testnet GRC, and a swap through this terminal would move GRC the wrong way
anyway: the desk is the counterparty on every pair (see the section above), so a
BTC -> GRC swap pays GRC OUT of 25779.

## EVERY DOLLAR FIGURE ON THESE PAGES IS A MAINNET PRICE ON A TESTNET COIN

Measured 2026-10-07: the price feed returned `GRC_USD 0.00829536` and
`BTC_USD 83224.0`, and the terminal applied them to balances held on the Gridcoin
TEST chain and a Bitcoin REGTEST node.

That is not a defect to fix -- services/pricing.py has one source and it quotes
the real market, which is what a quote has to do if the rates are ever to mean
anything. It IS a reading that has to be made consciously, because the arithmetic
invites a category error:

    $1000 of GRC = 120,549.32 tGRC   at the mainnet price
    the desk holds        11.00 tGRC = $0.09 by the same arithmetic
    time to stake one block on 25779: 12,066.99 days = 33.0 years

So a target expressed in dollars is a target in mainnet GRC, and the coins
available to meet it are testnet coins with no market at all. "Get the hot wallet
to $1000" and "get the hot wallet to 120,549 tGRC" are the same sentence and only
the second one can be acted on -- from a faucet, since 33 years of staking and a
3,000-odd tGRC sibling wallet do not reach it.

## Flow of one swap

    customer page        quote_service         swap_service        deposit_watcher
    picks a pair   -->   price, then     -->   row written:  -->   chain confirms
    lamps: green /       150bps fee as a       awaiting_           deposit_seen
    yellow / red         SUBTRACTION from      deposit +           -> confirming
    from pair_view       gross output          deposit addr             |
    .asset_rollups()     (the fee is                                    v
                         already the                              payout_pending
                         desk's; it is                                  |
                         sent less)                                     v
                                                                    paying
                                                                        |
    payouts row    <--  payout_worker    <--  payout_capacity           |
    created ->          unlock context,       can the wallet      <-----+
    broadcast ->        then broadcast        still fund what
    completed           (irreversible)        it already owes?

Swap statuses, as the code writes them: `awaiting_deposit`, `deposit_seen`,
`confirming`, `payout_pending`, `paying`, `completed`, plus `expired`,
`under_review`, `failed`. `deposit_service.ACTIVE_STATUSES` is the first three.

TWO PAYOUT STATUS VOCABULARIES EXIST AND THE DIFFERENCE IS DELIBERATE:

    db.PAYOUT_LIVE_STATUSES                   ("created", "broadcast", "completed")
      governs `payouts` / idx_payouts_one_live_per_swap -- a row is CREATED and
      reserves inventory against itself
    swap_intents_schema.LIVE_PAYOUT_STATUSES  ("claimed", "broadcast", "completed")
      governs `swap_intent_payouts` / idx_swap_intent_payouts_one_live_per_intent
      -- exactly one payer CLAIMS a row before broadcasting

Same length, same last two elements, different first element, and names that
differ only by word order. Until 2026-10-07 neither file mentioned the other;
both now do, and the difference is asserted in
tests/test_payout_live_statuses_have_one_spelling.py so a tidy-up cannot merge
them silently.

## What this file states from CODE and not from a swap that happened

Two things, named so nobody reads the ICP column as a track record:

- **No ICP swap has ever been created.** `create_swap` with ICP as the source
  has never run. The ICP leg of the flow above is drawn from the code.
- **`* -> ICP` payouts need the desk's dfx identity placed on the host.** The
  ledger's `transfer` debits the CALLER, so a payout cannot be signed by the
  anonymous read identity the balance lookups use. That placement is the
  operator's (rule 16: armed state and live posture come back).
