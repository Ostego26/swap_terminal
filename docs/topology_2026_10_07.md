## Flow of one swap

    customer page        quote_service         swap_service        deposit_watcher
    picks a pair   -->   price, then     -->   row written:  -->   chain confirms
    lamps: green /       150bps fee as a       awaiting_           deposit_seen
    yellow / red         SUBTRACTION from      deposit +           -> confirming
    from pair_view       gross output          deposit addr             |
    .asset_rollups()     (the fee is                                    v
                         already the                              payout_pending
                         desk's; it is                                  |
                         sent less)                                     v
                                                                    paying
                                                                        |
    payouts row    <--  payout_worker    <--  payout_capacity           |
    created ->          unlock context,       can the wallet      <-----+
    broadcast ->        then broadcast        still fund what
    completed           (irreversible)        it already owes?

Swap statuses, as the code writes them: `awaiting_deposit`, `deposit_seen`,
`confirming`, `payout_pending`, `paying`, `completed`, plus `expired`,
`under_review`, `failed`. `deposit_service.ACTIVE_STATUSES` is the first three.

TWO PAYOUT STATUS VOCABULARIES EXIST AND THE DIFFERENCE IS DELIBERATE:

    db.PAYOUT_LIVE_STATUSES                   ("created", "broadcast", "completed")
      governs `payouts` / idx_payouts_one_live_per_swap -- a row is CREATED and
      reserves inventory against itself
    swap_intents_schema.LIVE_PAYOUT_STATUSES  ("claimed", "broadcast", "completed")
      governs `swap_intent_payouts` / idx_swap_intent_payouts_one_live_per_intent
      -- exactly one payer CLAIMS a row before broadcasting

Same length, same last two elements, different first element, and names that
differ only by word order. Until 2026-10-07 neither file mentioned the other;
both now do, and the difference is asserted in
tests/test_payout_live_statuses_have_one_spelling.py so a tidy-up cannot merge
them silently.

## What this file states from CODE and not from a swap that happened

Two things, named so nobody reads the ICP column as a track record:

- **No ICP swap has ever been created.** `create_swap` with ICP as the source
  has never run. The ICP leg of the flow above is drawn from the code.
- **`* -> ICP` payouts need the desk's dfx identity placed on the host.** The
  ledger's `transfer` debits the CALLER, so a payout cannot be signed by the
  anonymous read identity the balance lookups use. That placement is the
  operator's (rule 16: armed state and live posture come back).
